## 1. Что показала проверка 11.10 и почему нужна версия 2

Код v1.0 запускается: тесты проходят, дашборд открывается, бот отвечает. Но на живых данных он показывает артефакты, а не засуху. Причин четыре.

| № | Проблема | Измерено 11.10 |
|---|---|---|
| 1 | «Норма» и «сейчас» приходят из разных моделей (ERA5-Land и IFS) | Шардара: 0,443 против 0,188 м³/м³ за те же дни. Кызылорда: текущее значение ниже 30-летнего минимума нормы. У 3 районов из 8 перцентиль прибит к 0 или 100 |
| 2 | Летом у влажности почвы в ERA5-Land нет сигнала: модель не знает про полив, почва каждый год лежит на минимуме | У 7 районов из 8 разброс нормы в августе–сентябре не больше 0,013 м³/м³. Из 400 «засух» детектора за 1991–2020 годы 168 приходятся на июнь–ноябрь, и за ними стоит изменение в 0,001–0,002 м³/м³, то есть шаг округления API |
| 3 | Карта открывается в точке 0°, 0° | `plotly` 7.1.0 перестал центрировать `scatter_map` сам; в 5.24 и 6.3 работало |
| 4 | С 00:00 до 05:00 по Казахстану живой режим молча переключается на демо | Код берёт локальную дату, API принимает дату только по UTC и отвечает ошибкой 400 |

Проблемы 3 и 4 чинятся за час. Проблемы 1 и 2 требуют сменить сам показатель, по которому считается риск. Это главное решение версии 2.

## 2. Главное решение: риск считается по водному балансу, а не по влажности почвы

### 2.1. Новый показатель

**Водный баланс за 14 дней (ВБ14)** — сумма за 14 дней величины «осадки минус испаряемость», в миллиметрах.

- **Испаряемость (ET0)** — сколько воды испарил бы хорошо политый луг при данной жаре, ветре, сухости воздуха и солнце. Это стандартная величина ФАО (метод Пенмана — Монтейта), по ней во всём мире считают нормы полива.
- **Низкий ВБ14** означает, что атмосфера забирает воды намного больше, чем приносит дождь. Для поливного хозяйства это прямой сигнал: воды понадобится больше обычного.
- **Перцентиль ВБ14** считается так же, как в v1.0: текущее значение сравнивается со всеми значениями за 1991–2020 годы в окне ±15 дней от того же дня года. Низкий перцентиль означает «суше обычного».

Движок риска остаётся прежним: низкий перцентиль — сухо, резкое падение — внезапная засуха. Меняется только то, что в него подаётся.

### 2.2. Почему именно он

| Свойство | Влажность почвы (v1.0) | Водный баланс (v2.0) |
|---|---|---|
| Сигнал летом | Нет: норма плоская | Есть: в июле в Мактаарале испаряемость за 14 дней менялась от 92 мм (2002) до 113 мм (2018) |
| Согласованность источников | Расхождение в разы | ET0 в ERA5, IFS и EC46 расходится на 1–8 %, корреляция 0,95–0,99 |
| Прогноз на 44 дня | Только среднее по ансамблю | Все 51 сценарий ансамбля ECMWF, отсюда вероятность |
| Известная засуха 2021 года | Не проверялось | По ВБ14 2021 год — самый сухой сезон из 35 в Кызылорде и Мактаарале и второй в Сайраме (предварительный расчёт, закрепляется задачей S1) |
| Совместимость с Earth-2 | У многих погодных AI-моделей влажности почвы на выходе нет (уточняется в задаче E2-1) | Нужны только температура, влажность воздуха, ветер, радиация и осадки — стандартные выходы погодных моделей |

Научная основа: связь испаряемости с быстрым развитием засухи описана в работах по индексу EDDI (Hobbins et al., 2016; McEvoy et al., 2016), баланс «осадки минус испаряемость» лежит в основе индекса SPEI (Vicente-Serrano et al., 2010). Формулировки перед выносом на слайд сверить с первоисточниками.

### 2.3. Что это меняет в продукте и питче

- Фраза «следим за влажностью почвы» заменяется на «следим за водным балансом: сколько воды забирает атмосфера и сколько приносит дождь».
- Сообщение фермеру становится конкретнее: «дефицит влаги за 14 дней 96 мм при норме 84 мм, на 14 % выше» вместо абстрактного перцентиля.
- Вероятность берётся из ансамбля ECMWF: «32 из 51 сценария показывают засушливый период». Слова «AI-вероятность» не используются, пока своей модели нет.
- Влажность почвы из расчёта риска убирается. Вернуть её как второй показатель для весны можно после 12.10 (раздел 9).

### 4.2. `config.py`

Убрать `SOIL_VAR`. Добавить:

```python
ET0_VAR, PRECIP_VAR = "et0_fao_evapotranspiration", "precipitation_sum"
BALANCE_DAYS = 14                 # окно суммирования
BASELINE_START, BASELINE_END = 1991, 2025   # что лежит в файлах
CLIM_START, CLIM_END = 1991, 2020           # что считается нормой
CLIM_WINDOW_DAYS = 15
RECENT_DAYS = 75                  # 60 дней на графике + 14 на окно
FORECAST_DAYS = 46                # API отдаёт 44 заполненных дня
EC46_PAST_DAYS = 60               # перекрытие для поправки смещения
AI_FORECAST_DAYS, AI_PAST_DAYS, AI_ANCHOR_DAYS = 16, 3, 7   # AI-ансамбль AIFS
SCALE_CLIP = (0.80, 1.25)

FD_HIGH_PCT, FD_LOW_PCT, FD_WINDOW_DAYS = 40, 20, 20
FD_MIN_DRY_DAYS = 7               # сколько дней подряд должно быть сухо; откалибровано в S1
ONGOING_PCT = 10
P_HIGH, P_MODERATE = 0.50, 0.25   # доля сценариев

SEASON_START, SEASON_END = (4, 1), (9, 30)  # поливной сезон; уточнить у агронома
```

Все пороги — начальные значения. Пороги по наблюдениям (`FD_*`, `ONGOING_PCT`) калибрует задача S1. Пороги по вероятности (`P_HIGH`, `P_MODERATE`) откалибровать нельзя, пока нет архива прошлых прогнозов; в README это написано прямо.

### 4.3. `data.py` (M1, M2, M3, S3)

**Дата.** Везде использовать `datetime.now(timezone.utc).date()`. Локальная дата не используется нигде.

**Запрос.** `_get(url, params)`:
- сначала читает JSON и берёт поле `reason`, потом проверяет код ответа, чтобы текст ошибки не терялся;
- до 3 попыток с паузами 1 и 3 секунды при таймауте, коде 429 и кодах 5xx; ошибки 4xx не повторяются;
- при отказе бросает `DataError` с причиной и пишет предупреждение в журнал (`logging`).

**База нормы.** `load_baseline(region)` читает `data/baseline/<id>.csv.gz` со столбцами `date, et0, precip`. Файлы лежат в репозитории, поэтому первый запуск на сервере не делает тяжёлых запросов. Если файла нет, функция скачивает его и сохраняет.

**Текущие данные.** `fetch_recent(lat, lon, today)` делает два запроса к архиву за 75 дней по вчерашний день (сумма за сегодня ещё неполная):
- с `models=era5` — та же модель, что и норма; отстаёт примерно на 6 дней;
- без `models` — IFS; доходит до сегодняшнего дня.

Результат: значения ERA5 там, где они есть; последние дни берутся из IFS. ET0 из IFS умножается на коэффициент `k_ifs = ΣET0(ERA5) / ΣET0(IFS)` по общим дням, с ограничением `SCALE_CLIP`. Осадки не масштабируются.

**Прогноз.** `fetch_forecast(lat, lon)` запрашивает `models=ecmwf_ec46`, `forecast_days=46`, `past_days=60`. Ответ содержит по 51 ряду на переменную: ряд без суффикса (контрольный сценарий) и `_member01…50`. Функция возвращает две таблицы «дата × сценарий» для будущих дат и коэффициент `k_fc = ΣET0(текущие) / ΣET0(EC46, прошлые дни, среднее по сценариям)` с тем же ограничением. Если общих дней меньше 30, коэффициент равен 1 и это пишется в журнал.

**Режим повтора.** `load_region(region, mode="replay", replay_date=D)` не делает запросов. «Текущие данные» — строки базы за D−75…D, «прогноз» — фактические строки базы за D+1…D+44 как один сценарий. Результат помечается `source="replay"`.

**Снимок (S3).** После каждого удачного живого расчёта результат сохраняется в `data_cache/last_good_<id>.json` с временем.

**AI-ансамбль (S6).** `fetch_ai_ensemble(lat, lon)` запрашивает ансамблевый API с `models=ecmwf_aifs025`, `forecast_days=16`. Ответ: 51 сценарий AI-модели ECMWF AIFS (контрольный и 50 возмущённых), 14–15 заполненных дней, те же две переменные. Сравнить его с наблюдениями не на чем: прошлых дней API отдаёт только три. Поэтому ET0 AI-ансамбля приводится к уровню EC46 по первым 7 общим дням прогноза. Если запрос не удался, расчёт идёт без AI-ансамбля, и это пишется в журнал.

**Порядок отказа.** `load_region(region, mode="live")` возвращает первое, что получилось:
1. живые данные, `source="live"`;
2. снимок не старше 48 часов, `source="snapshot"`;
3. повтор `REPLAY_DEFAULT_DATE`, `source="replay"`.

Синтетический генератор `demo_region()` удаляется. Требование «демо никогда не падает» теперь выполняется повтором реального эпизода из локальных файлов, без выдуманных чисел.

Поле `demo: bool` заменяется полем `source` со значениями `live`, `snapshot`, `replay` и полем `as_of` (дата последнего наблюдения).

### 4.4. `balance.py` (M3)

| Функция | Что делает |
|---|---|
| `daily_balance(df)` | `precip − et0`, мм/сутки |
| `rolling_balance(s, days=14)` | Скользящая сумма; первые 13 значений отбрасываются |
| `clim_balance(baseline)` | ВБ14 по строкам 1991–2020 |
| `member_paths(recent, fc_et0, fc_precip)` | Для каждого сценария: склеить текущие данные и прогноз, посчитать ВБ14, оставить будущие даты. Результат — таблица «дата × сценарий». Поправки смещения применяются раньше, в `data.py` |
| `norm_deficit(clim_b14, date)` | Медиана дефицита (`−ВБ14`) нормы в окне ±15 дней |

Индекс считается по каждому сценарию отдельно, а не по среднему ансамбля. Проверено 11.10 в Мактаарале и Сайраме: в среднем ансамбля дождь идёт 6–8 дней из 14, а в отдельных сценариях 2–3 дня. Среднее размазывает осадки и занижает засуху.

### 4.5. `drought.py` (M4)

**Событие в сценарии.** Сценарий содержит засушливый период, если выполнены оба условия:
- `detect_onset` нашёл дату, где перцентиль упал с ≥ 40 до ≤ 20 за 20 дней или быстрее;
- после этой даты перцентиль остаётся ≤ 20 не меньше `FD_MIN_DRY_DAYS` дней подряд; если до конца прогноза осталось меньше дней, все оставшиеся должны быть ≤ 20.

**Вероятность.** `p_dry` — доля сценариев с событием. В режиме повтора сценарий один, вероятность не выводится.

**Уровень риска.**

| Уровень | Условие | Эмодзи |
|---|---|---|
| `ongoing` | перцентиль сейчас ≤ 10 | 🟤 |
| `high` | `p_dry` ≥ 0,50 | 🔴 |
| `moderate` | `p_dry` ≥ 0,25 или перцентиль сейчас ≤ 20 | 🟡 |
| `low` | остальное | 🟢 |

**Поля `Assessment`.**

| Поле | Значение |
|---|---|
| `level` | уровень риска |
| `current_pct` | перцентиль ВБ14 на последнюю дату наблюдений |
| `deficit_mm`, `norm_mm`, `anomaly_pct` | дефицит сейчас, норма, отклонение в процентах; отклонение равно `None`, если норма меньше 10 мм |
| `p_dry`, `n_members`, `n_dry` | вероятность, число сценариев, число сценариев с событием |
| `onset_date`, `days_to_onset` | медиана дат начала по сценариям с событием; выводится, если `p_dry` ≥ 0,25 и засуха ещё не идёт |
| `in_season` | попадает ли сегодняшняя дата в поливной сезон |
| `source`, `as_of` | откуда данные и на какую дату |
| `timeline` | таблица: дата, тип (`observed` / `forecast`), перцентиль (для прогноза — медиана сценариев), `p10`, `p90` |
| `ai` (S6) | `None` или словарь: `n_members`, `n_dry`, `p_dry` и таблица «дата, медиана, p10, p90» по AI-ансамблю на 14 дней |

**AI-ансамбль и уровень риска (S6).** Событие в сценарии AIFS считается по тому же правилу на горизонте 14 дней. Результат показывается рядом как второе мнение и **на уровень риска не влияет**: модель у нас не проверена на истории, а её ET0 на первой неделе расходится с ансамблем IFS на величину до 13 % (измерено 11.10).

### 4.6. `advice.py` (M5)

Формат сообщения (пример на русском):

### 4.10. Скрипты (M2, S1)

**`scripts/build_baseline.py`.** Для каждого района скачивает из архива с `models=era5` суточные `et0_fao_evapotranspiration` и `precipitation_sum` за 1991–2025 годы и пишет `data/baseline/<id>.csv.gz`. Между районами пауза 15 секунд, чтобы не упереться в лимит запросов.

**`scripts/history.py` (S1).** Работает только по файлам базы, без сети.
1. Считает перцентиль ВБ14 за 1991–2025 годы по норме 1991–2020.
2. Строит каталог засушливых периодов по правилу из раздела 4.5 с паузой 30 дней между событиями: район, дата начала, длительность, минимальный перцентиль, падение в мм.
3. Считает частоты: событий на район за поливной сезон; доля дней сезона с перцентилем ≤ 10 и ≤ 20.
4. Калибровка: пороги 40/20/20 из литературы не трогаются; подбирается только наш параметр `FD_MIN_DRY_DAYS` по 1991–2014 годам так, чтобы событий было от 0,5 до 1,5 на район за сезон. 2015–2025 используется только для проверки.
5. Выбирает эпизод для повтора по правилу «самый длинный засушливый период поливного сезона 2021–2025»; повтор начинается за 14 дней до него. Первоначальное правило «по падению в мм» отклонено после первого прогона (см. статус в начале документа); его результат сохраняется в отчёте.
6. Сохраняет `reports/dry_spell_catalog.csv`, `reports/seasons_ranking.csv`, `reports/events_per_year.png`, `reports/case_<район>_<год>.png`, `reports/calibration.json`.

## 5. Нефункциональные требования

- Python ≥ 3.10 (проверено на 3.10.0).
- Приложение не падает при любой сетевой ошибке: срабатывает порядок отказа из раздела 4.3.
- Синтетических данных в продукте нет. Всё, что видит пользователь, — живые данные, их снимок или реальная история с явной пометкой.
- Расчёт одного района на живых данных: не дольше 10 секунд (три запроса; 11.10 каждый занимал 0,5–1 секунду).
- Каждая сетевая ошибка попадает в журнал с причиной.
- Бот не хранит геолокацию; язык хранится в памяти процесса.
- Данные Open-Meteo бесплатны только для некоммерческого использования. Для коммерческого запуска нужен платный тариф или прямой доступ к ECMWF.

Чего мы пока не знаем: какие именно переменные выдают `FuXiS2S` и `DLESyM` и на какой срок. Это первая задача этапа (E2-1).

- **GPU с памятью от 40 ГБ у команды нет** (подтверждено 11.10), а на рабочем ноутбуке нет GPU NVIDIA и стоит Python 3.10. Чем это заменяется сейчас — в разделе 10.2;

### 10.2. Пока нет GPU: чем заменяем Earth-2

Что AIFS не заменяет: его горизонт — 2 недели, а не 6, и у нас нет проверки его качества на истории. Субсезонные AI-модели (`FuXiS2S`, `DLESyM`) на 6 недель по-прежнему требуют своего запуска на GPU.

### 10.3. Как Earth-2 встраивается в AquaTwin

Расчёт риска уже в версии 2 принимает на вход таблицу «дата × сценарий» с ET0 и осадками и не знает, откуда она пришла. Earth-2 становится вторым поставщиком таких таблиц.

```
Open-Meteo: ECMWF EC46, 51 сценарий ───────────────┐
                                                    ├─► balance.member_paths ─► drought.assess ─► дашборд, бот
GPU: Earth2Studio, FuXi-S2S или DLESyM, N сценариев ┘
     │
     └─ температура, влажность, ветер, радиация, осадки ─► ET0 по ФАО ─► файлы по районам
```

Запуск моделей идёт пакетно на GPU по расписанию, результат сохраняется в файлы. Дашборд и бот только читают файлы, поэтому им GPU не нужен.

## Приложение 1. Проверенные запросы к API (11.10.2026)

Норма и текущие данные из одной модели:
```
https://archive-api.open-meteo.com/v1/archive?latitude=40.67&longitude=68.55
  &start_date=1991-01-01&end_date=2025-12-31
  &daily=et0_fao_evapotranspiration,precipitation_sum&models=era5&timezone=auto
```

Последние дни (IFS, до сегодняшней даты по UTC):
```
https://archive-api.open-meteo.com/v1/archive?latitude=40.67&longitude=68.55
  &start_date=<сегодня−75>&end_date=<сегодня по UTC>
  &daily=et0_fao_evapotranspiration,precipitation_sum&timezone=auto
```

Прогноз, 51 сценарий, с прошлыми днями для поправки смещения:
```
https://seasonal-api.open-meteo.com/v1/seasonal?latitude=40.67&longitude=68.55
  &daily=et0_fao_evapotranspiration,precipitation_sum&models=ecmwf_ec46
  &forecast_days=46&past_days=60&timezone=auto
```

AI-ансамбль ECMWF AIFS, 50 сценариев на 14 дней (S6):
```
https://ensemble-api.open-meteo.com/v1/ensemble?latitude=40.67&longitude=68.55
  &daily=et0_fao_evapotranspiration,precipitation_sum&models=ecmwf_aifs025
  &forecast_days=16&timezone=auto
```

Свойства ответов:
- AI-ансамбль: 50 сценариев, 14 заполненных дней, 16 КБ за 0,5 секунды; `past_days` отдаёт только 3 прошлых дня; модель `gfs_graphcast025` нужных суточных переменных не отдаёт;
- архив с датой окончания позже сегодняшней по UTC отвечает кодом 400;
- ERA5 отстаёт на 6 дней, IFS доходит до сегодня;
- прогноз: 102 ряда, 44 заполненных будущих дня, ответ 62 КБ за 0,5 секунды;
- ряд без суффикса — контрольный сценарий, а не среднее;
- сезонный API принимает даты начиная с 01.09.2025.

## Приложение 3. Глоссарий

- **ET0, испаряемость** — эталонное испарение с политого луга по методу ФАО-56 (Пенман — Монтейт), мм/сутки.
- **ВБ14** — водный баланс за 14 дней: сумма «осадки − ET0», мм. Чем ниже, тем суше.
- **Дефицит** — то же с обратным знаком: «ET0 − осадки».
- **Перцентиль** — место текущего значения среди исторических; 20-й перцентиль означает, что суше было только в 20 % случаев.
- **ERA5** — реанализ ECMWF: восстановленная история погоды с 1940 года, сетка около 25 км.
- **IFS** — оперативная модель ECMWF, сетка 9 км.
- **EC46** — субсезонный ансамблевый прогноз ECMWF на 46 дней, 51 сценарий.
- **Ансамбль, сценарий** — один и тот же прогноз, посчитанный много раз с чуть разными начальными условиями; разброс сценариев показывает неопределённость.
- **Засушливый период** — событие из раздела 4.5.
- **Повтор (replay)** — показ реальных исторических данных на выбранную дату; не прогноз.
- **Earth2Studio** — открытый пакет NVIDIA для запуска AI-моделей погоды.
- **CorrDiff** — модель NVIDIA для повышения разрешения прогноза (даунскейлинг).
